# oura-coach — Project Brief (source of truth)

## Goal
Every morning the agent pulls my Oura data (sleep, readiness, HRV, resting HR, intraday heart rate, stress, activity, workouts) and my Google Calendar. It compares today against my 7-day baseline and my goals in goals.yaml (half-marathon plan, body-composition goal, training rules), checks in with me on Telegram (energy, soreness, food), then gives a plan: workout type (HIIT / easy run / long run / walk / rest), time slot (I prefer mornings), and a short nutrition note. It remembers temporary context with an expiry (e.g., "traveling Thu-Sat, keep it light") and logs every day so it can learn patterns over time.

**Food logging (core requirement):** I log everything I consume, several times a day: meals, snacks, drinks, coffee, alcohol, supplements. Each entry gets a rough LLM estimate (protein, fiber, carbs, calories, caffeine, alcohol drinks, entry type, confidence) saved to `food_log`. Every entry is saved, repeats included, and confirmed back with the estimate. Today: `python log_food.py "text"`. M3: free-form Telegram messages that describe food go through the same `food.log_food()`.

## Stack
Python 3.11+, LangGraph (langgraph, langgraph-checkpoint-sqlite), langchain-openai (ChatOpenAI), python-telegram-bot, httpx, icalendar (+ recurring-ical-events), apscheduler, python-dotenv, pyyaml, SQLite.

## Milestones
- **M1 Data layer:** Oura client, calendar free slots, SQLite, smoke test
- **M2 Agent brain:** LangGraph fetch -> assess -> plan -> log, runs in the terminal
- **M3 Telegram:** check-in any time with interrupt (plan for now), free-form messages (food, notes, workouts done, questions), context notes with expiry
- **M4 Always-on:** one long-running process (Telegram listener + 7am APScheduler job), error alerts to Telegram, deployable to a Raspberry Pi or a small cloud host
- **M5 Learning:** weekly reflection that saves insights, food/sleep correlations

## Rules

- Work on ONE milestone at a time. Never start the next one without the user's go-ahead.
- Never invent API fields or endpoints. For Oura, save real responses to fixtures/ and build parsing from those. If unsure, say so and ask.
- Deterministic code for math and time (baselines, free slots); the LLM only for reasoning and wording.
- Never print, log, or commit secrets (this includes the iCal URL).

## Decisions
- Oura `/sleep` endpoint is fetched in addition to `daily_sleep`: HRV and lowest heart rate live on sleep periods, not on the daily score.
- Oura refresh tokens are single-use: tokens live in SQLite (`tokens` table, seeded from .env on first run) and each new pair is saved in one transaction right after a refresh.
- Oura parsing is built only from fields observed in fixtures/. `personal_info` is fetched on every run (age, weight in kg, height in m; units judged from the values).
- Calendar recurrence is expanded with `recurring-ical-events`.
- Free slots: gaps of at least 30 min within 06:00–21:00 America/Chicago. All-day events are listed for information and do not block slots. Events marked "free" (TRANSP:TRANSPARENT) are ignored.
- fixtures/ is gitignored (personal health data). fixtures/calendar.ics holds the raw feed content (saved by the smoke test), never the URL.
- **Models (M4 Part B):** `config/models.yaml` maps each job to a provider + model: classifier, agent, structured (`core/llm.structured_call`), judge (gpt-5), embeddings (text-embedding-3-small), template_draft (declared, unused). `core/models.py` is the only place models are made. Precedence: a skill file's `model` (agent only) > `OPENAI_MODEL` in .env (classifier, agent, structured, as before) > models.yaml. Prices per model live in models.yaml (USD per 1M tokens, checked 2026-11-08); `models.cost`. Every `runs` row records kind, job, model, input/output tokens and latency. No temperature is set (gpt-5 models reject non-default values).
- LLM proposes, code enforces: `policy.py` applies the hard rules after the LLM plan and records every override. Code computes all numbers, times, dates and rules; the LLM only proposes, explains and words things.
- **Plan for now (M3):** every plan is for a workout starting now. Plan window (`calendar_client.plan_window`) = from now (or the end of the current event, chained through back-to-back events) until the next event or 21:00. A gap under 30 min jumps to the next free gap; nothing left = rest. The plan may start later inside the window; otherwise it moves to the window start; duration is clamped to the window. Rest = slot "none", 0 min. `preferred_time` in goals.yaml is no longer used for planning.
- **Sessions table:** one row per check-in (status awaiting_checkin → planned, or abandoned) and per unplanned workout (status unplanned). Per-plan data (check-in, plan, LLM plan, overrides, completed, feeling, actual times) lives here; `daily_log` keeps day-level data only (metrics_json, food_targets_json).
- **Migration:** `db.init_db()` detects an older schema (M2 daily_log columns, missing `food_log.logged_at`, or missing `sessions.done_by/details_json`), copies the file to `<name>.backup-YYYYMMDD-HHMMSS.db` first (prints the path; aborts if the backup fails), then moves daily_log plans into sessions, drops the old daily_log columns, and adds `food_log.logged_at`. Never migrate without the backup.
- **Activity (`activity.py`):** today's activity = Oura workouts merged with done plan blocks and manual workouts; an Oura workout that overlaps one in time is the same activity. Each done block is its own item (its own times). A plan never marked done does not count. A workout added in chat without minutes gets the usual length for its type (`blocks.default_minutes`, the same defaults as requested plans).
- **Hard day** = any block that is HIIT, long_run, intensity >= 4, an Oura `running` of 60+ min, or a chat-reported run of 60+ min (`activity.hard_oura` in goals.yaml). Used by "no back-to-back hard days" (yesterday's merged activity) and the weekly cap (`max_hard_days_per_week` over today + the previous 6 days of merged activity). A downgraded hard day becomes easy_run, intensity <= 3.
- **Walk rule:** a walk of 20+ min (Oura `walking` or a chat-logged walk) is a light workout, never hard. It counts toward "already worked out today" only when today's band is not PUSH (`activity.walk_counts` in goals.yaml). Shorter walks never count. Every non-walk workout (Oura or done session) counts.
- **Rule a, already worked out today:** anything but walk / mobility / rest becomes walk; intensity <= 2.
- **Rule c, recent food (`recent_food_caps` in goals.yaml):** an entry with at least `min_calories` eaten within `within_min` caps intensity at `max_intensity`; the strictest match wins. Cap <= 2 = walk / mobility / rest only; cap 3 = HIIT becomes easy_run. Calories, not entry_type, so coffee and supplements never cap.
- Policy order: readiness floor → band (effective) → already worked out → back-to-back → weekly cap → long run on weekends → recent food → plan window.
- **Effective band (M3.1, `baseline.effective_band`):** the check-in lowers (never raises) the Oura band. Energy <= 2 or soreness >= 4 → recover; else energy <= 3 or soreness >= 3 → one level down (goals.yaml `checkin`). Unanswered values are ignored. Computed in `gather_today`, passed to the plan prompt, enforced by policy_check (recover: walk/mobility/rest <= 2; maintain: no HIIT, <= 3) with the check-in as the stated reason. The walk rule uses the effective band.
- **Overrides** are `{rule, text, plain, changes_type}`: `text` technical (run.py), `plain` a coach sentence (chat). The deciding override = the last one that changed the workout type, or "no free time". Old sessions with string overrides still display.
- **Chat message (M3.1):** short plan message from `chat.format_plan` (readiness, workout line, "Today:" targets on the first plan of the day, one Why line, food lines, a closing line); no band label, human labels and 12-hour times (`labels.py`). Why = the LLM's `why`, or the deciding override's plain sentence when code changed the type, prefixed "Your body could handle more, but…" when the Oura band is not recover and readiness >= floor but a non-body rule decided. If code changed the type, food lines are code-picked (`nutrition.fallback_before/fallback_meal`), never the LLM's. Rest plans end with a question (LLM `follow_up`, or a fixed one), which stays in the chat session so a bare "yes" is understood. The `explain_plan` tool shows everything from `plans.details_json`. (Formatters live in `modules/training/messages.py`.) Nothing the person reads may contain snake_case, "null" or "window" (tested).
- **Planner graph (M3.2):** fetch_data → compute_baseline → gather_today → `rest_plan` (late or no free time) | `suggested_plan` (they said no) | `consult` (they asked for a workout) | `plan` → policy_check → log; `consult` → END (question) or `plan`. Only `plan` calls the LLM. No interrupt and no checkpointer: it runs only once the check-in is known (`planner.run_plan`, `planner.answer_consult`); a given `plan_id` (the pending row) is filled instead of a new row.
- **Check-in parsing (`modules/training/checkin.py`):** `submit_checkin(answer)` gets their words exactly as written. A bare "4 2" or "skip" is read by code; anything else is one structured LLM call (`prompts/checkin.md`) → energy 1–5, soreness 0–5 (0 is valid), request (blocks in their order; "run" = easy_run), feeling (saved as the note), constraints (to the plan prompt only). The request can also come from `start_checkin(request_text)` ("want HIIT"), saved on the row. Out-of-range numbers: the tool asks again.
- **Consult once (M3.2 Phase 3):** a request is first checked in code (`planner.consult`, no LLM): default intensity per type (HIIT 5, long_run 4, easy_run/strength 3, walk 2, mobility 1) and minutes (HIIT 30, long_run 75, easy_run 40, strength 45, walk 30, mobility 20; yoga/other 30) when not given. A conflict = an override that changes a type, or a hard request made easy; the clock never counts. Then the row is `awaiting_confirm` and `requested_json` holds the request, the code-built suggestion plan and its overrides. The question is built from them: `{reasons, at most 2; the band reason is dropped when readiness is low}\nI'd suggest {suggestion} instead. Still want {request}?`, in plain words only (e.g. "Readiness is 64 today, lower than usual, so I'd keep it light." — "lower than usual" vs the 7-day average, else "on the low side"; never "floor"). `confirm_override`: yes → the LLM plans the request, only the clock applies, each skipped rule saved as `{rule: user_choice, skipped}`; no → the stored suggestion as offered (code, no LLM), moved to start now. It refuses when the question was asked in the same turn (the model can't answer for them). A question lasts 2 h (`CONSULT_TTL_MIN`), across chat sessions; unanswered, `db.expire_consults` (called in `ingest` and the training tools) sets it `expired`: no plan is made, nothing is sent, nothing counts toward the score. A later "yes" gets "That question expired, so nothing was planned…". A new check-in abandons it.
- **Blocks:** a plan with several parts has `plan_json.blocks` (in order); its top-level fields are a summary (the hardest block's type, max intensity, total minutes, whole slot). A single-block plan has no `blocks` key. Blocks come only from a request (the coach's own blocks are ignored without one). The type rules run per block, same-type neighbours merge (two walks → one walk), the hard-day rules downgrade every hard block, and the window cuts the last block (a block left under 10 min is dropped, never the first). With a request, code pins the blocks to it (types and order from the request, minutes from the request or else the coach); if the coach proposed other types, its why and food lines are replaced by code.
- **Late (`planner.is_late`):** after the day's `score_cutoff` (21:00) or before 06:00, with day = `day_of(now)` (so 00:30 before that night's sleep is still yesterday). Rest + a sleep note ("It's late, so no workout now." / "Get some sleep and check in again in the morning."), no LLM call, no consult, no check-in question; a late check-in doesn't abandon the day's plans. No free time + a request → rest that says "There's no free time left today for {request}."
- **A new check-in abandons** today's plans with nothing done (and any waiting question); Oura completions are synced first, so a recorded workout is done, not abandoned.
- **Strength:** `strength` is a plan type (not hard unless intensity >= 4; becomes walk on recover / already-trained days; a hard-day downgrade keeps strength at intensity <= 3). Split Push / Pull / Legs (goals.yaml `strength.split`); code picks the day after the last done strength block that recorded one (`activity.next_split_day`). The LLM lists exercises; code shows them only if there are 5-6, and clears them if the type changed.
- **Oura auto-complete, per block:** `today.sync_oura_completions` (the one write in the read path, idempotent) marks a not-done block of today's open plans done (`plan_blocks_done`, `done_by = oura`, Oura's times) when Oura records a matching workout (runs ↔ running, walk ↔ walking, strength ↔ strengthTraining, HIIT/mobility ↔ any) overlapping that block's own slot ± 60 min. Each Oura workout completes one block. When every block is done the plans row gets `completed = 1`, actual_start/end spanning the blocks, `done_by` oura / chat / mixed. Older rows marked done as a whole (no block rows) count as one done block. `plan_blocks_done` is a new table (CREATE IF NOT EXISTS), so no migration.
- `mobility` is a workout type (never hard), allowed wherever walk is.
- Readiness band (`baseline.readiness_band`, deterministic) cuts LLM variance. "Worse than baseline" = readiness/HRV/sleep below, or resting HR above (lower RHR is good).
  - recover: readiness < readiness_floor, or 2+ metrics worse. Policy: walk, mobility or rest only (intensity <= 2).
  - push: readiness and HRV normal or above, nothing worse. Policy: anything the other rules allow. The prompt steers push to HIIT on weekdays / long_run on weekends unless other rules or the check-in say otherwise.
  - maintain: everything else, including missing readiness or HRV. Policy: no HIIT, intensity <= 3.
  - The band and its reason go to the LLM and are printed in the report.
- Readiness floor comes from `goals.yaml` (`schedule.readiness_floor`, 70): below it, anything other than walk/mobility/rest becomes walk, intensity <= 2.
- Long run only on Sat/Sun; on weekdays it becomes easy_run.
- Baseline = average of the 7 days before today, skipping missing values. Status thresholds: readiness and sleep score ±5 points, HRV ±10%, resting HR ±3 bpm (lower resting HR is good).
- **Food targets (`modules/nutrition/targets.py`):** Mifflin-St Jeor BMR from Oura personal_info (goals.yaml `nutrition.weight_kg` overrides the weight if set) × `activity_factor` − `deficit_kcal` (never below BMR); protein = kg × `protein_g_per_kg`; fat = `fat_pct` of calories; carbs = the rest; fiber per 1000 kcal. Same targets every day (no active-calorie adjustment). Remaining = targets − food so far, floored at 0 (no fat: food logs have no fat estimate). First plan of the day shows full targets + LLM meal ideas (saved diet facts); later plans show remaining + a pre/post note. Code-picked meals (no fitting LLM text) come from `config/meals.yaml` by diet and protein left, rotating by date and skipping recent ideas.
- Food: yesterday's and today's entries are summed in code. If today has no entries, the plan says so and food does not change the intensity.
- **Food time:** `food_log.timestamp` = when it was eaten: the message time, or a stated clock time (`timeparse.parse_clock_time`: the most recent past occurrence within 12 h; "1" at 14:10 = 13:00, at 09:00 = 01:00). `logged_at` = when it was saved (used by /undo).
- **Dates for dated memory facts:** the agent copies phrases ("Thu", "Sat"); `timeparse.resolve_dates` resolves them (weekday = next occurrence on/after today, the end on/after the start; "next Fri" = a week after that; "this weekend" = Sat–Sun; "Oct 12", "10/12"; missing = today). Unreadable dates are not saved; the bot asks again.
- **Agent (M3.2, `core/agent.py`):** ingest → `greet` (whole-message greeting only; code, no LLM; "no readiness yet" without data) | `agent` ⇄ `tools` (ToolNode) → `respond` → END. One LangGraph thread per chat session (`session-{user_id}-{YYYYMMDDHHMM}`, new after 15 quiet minutes); the model sees the conversation from the 5th-last user message; saved facts (with ids) and each enabled module's `context()` go in the system message every turn. Tools read user_id / now / session_id / use_fixtures from the run config. Tools of disabled modules are never shown to the model. The old router, chat.py and `/checkin /plan /food /note /undo /today /why` are gone.
- **Reply rules (`core/reply_rules.py`, enforced in `respond`):** ≤3 lines, ≤60 words, no internal terms (incl. "override"), no tacked-on "anything else?", no first-person claim ("I logged", "I synced", "I'll resend") without the matching tool this turn. A broken draft is rewritten once by the model, then trimmed by code. Text built by tools (check-in question, consult question, plan, explain_plan, mark_done) is sent exactly as built (ToolMessage artifact `verbatim`), first; the model's own line follows on its own line only when a write tool also ran (e.g. "done, what should I eat now?" answered in words), and is dropped if it just repeats the built text or if code text already covers both the writes and the rest (mark_done's confirmation + suggest_meal's ideas). Meal ideas and recipes are code-built text too.
- **Check-in as DB state:** `start_checkin` saves a `plans` row (awaiting_checkin, with its chat_session_id) and sends the fixed question; `submit_checkin(answer)` parses it and runs the planner on that row. A check-in question left open in an earlier session is abandoned at the next message (a consult question is not: it expires after 2 h); if it was today, the reply ends with "Still want to check in today?". `plan_workout` plans now from today's latest check-in (or "skipped").
- **Food logging (Phase 4):** numbers they state ("30 cal", "9g carbs": `log_food` / `edit_food` args calories, protein_g, carbs_g, fiber_g, caffeine_mg) replace the estimate for that field and are recorded in `food_log.user_numbers_json`; the estimate prompt is told them so the rest stays consistent. Confirmations show them as theirs ("30 kcal, 9 g carbs (your numbers); about 0 g protein"). Not a log: questions about a food, food they plan to eat later (prompt rules).
- **edit_food = in place, never a new row:** a new description (keeping the amount: "5 slices of cheese pizza with olives") or their doubt (`feedback`, "I don't think it's 60g protein") re-estimates every field they never stated; stated numbers, earlier and now, always win. A numbers-only edit makes no LLM call. `log_food` still refuses a message that reads as a correction once food was logged today (it points to edit_food).
- **Finding entries:** `edit_food` / `remove_food` only take ids shown in this conversation (log_food / list_food / edit_food results). `remove_food` also refuses when the picked entries share a dish (`targets.dish_key`) with another entry today and the message doesn't single them out (a time, "both", "the second", "last two"…): the agent asks. `list_food(day)` takes any past day as said ("Oct 10", "last Monday", "3 days ago") via `timeparse.resolve_past_day` (looks back only; "Oct 10" after Oct 10 is this year, before it last year).
- **Meal ideas (`modules/nutrition/meals.py`):** `suggest_meal(meal, ingredients, constraints)` → 1–2 dishes on different main ingredients, each with portions in grams + a household measure (katori, cup, chapatis), sized by code (`targets.meal_budget`: what's left today ÷ meals still to come — 3 before 11:00, 2 before 17:00, then 1 — capped at 35% of the day's target, at least 200 kcal). Inputs: saved diet facts, the 10 foods they log most (30 days), and `do_not_suggest` = dishes suggested in the last 5 days (`meal_suggestions`) + what they ate today or yesterday. Code drops any repeat (same `dish_key`, the dish's first name words), asks once more naming the rejected dishes, then falls back to `config/meals.yaml`. Suggestions are saved. `meal_recipe(dish, change, ingredients)` gives portions + ≤6 steps for that dish; the title is code's (the same dish, "(higher protein)" for a change). Both texts are sent as built. The plan prompt also gets `recent_meal_ideas` (no dish examples in prompts).
- **Nutrition score (`modules/nutrition/score.py`, pure `score_day`; `config/score.yaml` `nutrition`):** protein 40% (linear to the target), calories 40% (full within ±10% of the target at moderate rigor — light 15, intense 5 — sloping to 0 at ±30% — light 40, intense 20; after the cutoff, under 0.6 × target = 0, never reward under-eating), meals 20% (meal/snack entries, full at 3). Nothing logged = 0, note "not logged". No targets = meals part only. Module `score(user, day, now=None)`: `now` decides whether the cutoff has passed (None = a past day).
- **Daily score (`core/score.py`, M3.2 Phase 5):** 0–100 = weighted sum of components (`config/score.yaml` templates by `goal_template` + `goal_rigor`; moderate: training 35, nutrition 30, recovery 20, movement 15). `compute_score` is pure; the LLM only words the `get_score` result. Training / nutrition come from each enabled module's `score()`; recovery and movement are core (device data).
  - **Recovery = what they control, never raw readiness or sleep quality:** last night's Oura `time_in_bed` vs `bed_hours_target` (7.5 h moderate; 0 at 2.5 h short), last night's `bedtime_start` vs their usual (average of the earlier nights, ≥ 3; full within 30 min, 0 at 90), and — only on a low-readiness day (readiness < floor) — no hard workout = full. Weights 0.5 / 0.3 / 0.2, re-weighted when a part has no data. Low readiness or a restless night alone never lowers it.
  - **Movement** = Oura steps / `steps_target` (6k / 8k / 10k).
  - **Missing data:** a component with no data (no sleep, no steps, no activity data at all) is left out and the rest re-weighted, never 0. Food not logged is the exception (nutrition 0, "not logged": it's their own log).
  - **Hints, not guilt:** each component may carry `next`, a plain fact computed in code while the day is open ("a 20-minute walk (2,200 steps to go)", "your planned easy run", "about 40 g more protein", "bed close to your usual 11:30pm tonight"); the agent words at most one kindly. Notes say "still to do" / "no workout yet" before the cutoff.
  - **Compared to their own past:** headline built in code, "74 so far, up from your 68 average" (average of their final scores over the 7 days before, once there are ≥ 3; "right at", "a little under"). No streaks, no comparison to others.
  - **Final:** a day is final once its `score_cutoff` (21:00) has passed. `finalize_due` runs in `ingest` (before the message's tools, so a 21:30 cookie can't change the day) and stores final scores (`daily_scores.final = 1`, never replaced) for every day in the last 7 since the first day they used the coach. `get_score` stores provisional scores too (overwritten until final). One Oura fetch serves all days (`Health(pinned=cache)`; `OuraSource` reads a pinned cache copy that covers the day). Failures there never block a message (`finalize_quietly` logs the error type).
- **`mark_done` = Oura-exact:** fetches Oura again, syncs, and confirms in code: "Marked done: HIIT 12:12–1:03pm (from Oura). How did it feel?", or "Oura doesn't have a matching workout. Want me to add it with a time?" (it names the block when there are several). It never invents times. `add_manual_workout` with the time they give completes only the open block of the same type (a manual strength never touches the run block; no manual row then); any other workout is a manual row.
- **Training score (`modules/training/score.py`, pure `score_day`):** per workout plan, credited minutes = sum over blocks of min(done, planned); ≥ 70% of the planned total = 1.0, some = 0.5 ("partly done"), none but another counting workout after the plan was made = 0.5, else 0. A coach-planned rest = 1.0, or 0 if a hard workout started after it was made; a code rest (late / no free time) is not a rest day and is ignored. Day = max(best plan, 1.0 if a counting workout started before the first plan). No plans: any counting workout (walks at 20+ min) = 1.0, else an inferred rest day (below). `TrainingModule.score(user, day, now)` syncs Oura first; no plans, no activity and no device data for the day = left out (None).
- **Rest days are inferred, never declared (M3.2 Phase 6):** a day with no plan and no counting workout is a rest day at full credit when it's a recovery rest — readiness < floor that day, or an active saved `context` fact covers it ("traveling", "sick"); these don't use the budget — or when the ordinary rest days in the 7 days ending today stay within goals.yaml `schedule.rest_days_per_week`. Otherwise 0 (while the day is open: "no workout yet" + the walk hint). A skipped planned session is scored by its plan. Days with no data at all count neither way. Notes: "Rest day — you've trained 6 of the last 7 days", "Recovery rest — readiness was 64", "no workout — 2 rest days in the last 7 (your week has 1)". No question to the user. Pure: `score.rest_week` / `recovery_reason`; the week is gathered in `TrainingModule._rest_week`.
- **Forget:** one thing ("forget the eggs thing") = one fact, the matching one saved most recently (facts are shown oldest first), removed without asking; a group ("my diet stuff") → list in plain words and ask, never ids. Code guard: `forget` with several ids refuses unless their message says both / all / everything. Undated "sometime soon" facts: `resolve_dates` can't read them, so nothing is saved and the agent asks which days.
- **Expired facts are not loaded:** the system prompt has the facts that apply today (`memory.facts(user, day)`); `list_memory` shows undated and not-yet-ended facts (`memory.current`), so a finished trip is never mentioned again (still in the DB). A dated fact that applies today is named in the plan's Why ("Since you're traveling, …").
- **Users:** `db.add_user(telegram_chat_id, name)` adds a person with default settings and no saved facts (user 1 keeps the seeded ones). Every tool, session and score is per user (scenario 32).
- **Scenario tests (`docs/scenarios.md` = the eval set):** every scenario has a scripted test (preset model turns: tools, DB, reply rules) and a live test (`RUN_LIVE_LLM=1`); `COVERAGE` in `tests/test_replay.py` maps each id to both and a test fails if the doc and the tests drift. M4 scenarios are live-only `xfail(reason="M4")`. `LIVE_RUNS=3` runs each live scenario 3 times and prints a pass-rate table (★ = `@core`, must pass every run). An LLM judge (`tests/conftest.judge`, yes/no) is used only for "did it answer what was asked". Live tests stub plan and food estimates unless a scenario is about them (`real_checkin`, `real_food`, `real_meals`, `real_plan`).
- **SQLite across threads:** every `db.py` call opens and closes its own connection (timeout 10 s, WAL), so `asyncio.to_thread` workers never share one. The checkpointer uses one `check_same_thread=False` connection; SqliteSaver locks around it.
- **Telegram:** handlers filter on `TELEGRAM_CHAT_ID` and resolve the sender with `users.for_telegram_chat`; commands: /start, /help (built from enabled modules); voice/audio → fixed "can't understand voice notes yet" reply; slow calls run in `asyncio.to_thread`; errors reply with the exception type only; logs go through `config.redact()`; httpx/telegram loggers at WARNING (Telegram URLs contain the bot token).
- `--fixtures` reads fixtures/ (Oura incl. personal_info + calendar.ics, or an empty calendar if it is missing) and writes only to `demo.db` / `demo_checkpoints.db`, never to `oura_coach.db`. The OpenAI call is still live. "Today" in fixtures mode = newest day in daily_readiness.json, with the current clock time (or `run.py --at HH:MM`). `log_food.py --demo` logs into demo.db on that day. `langgraph dev` (`studio.py`, graphs `agent` and `planner`) always uses fixtures + demo.db.

Categories, definitions and examples come from `skills/*.md` frontmatter at call time (a new file = a new category; `core/skills.py` loads and validates them; an unknown tool name fails at build). The agent gets only the union of the chosen skills' tools (of the user's enabled modules) and their bodies; a skill `model` overrides the agent model. In scripted tests a fake classifier reads this set (an unlabeled message fails the test) and `ScriptedChat` refuses any tool the route didn't offer, so every scenario proves its skill's tool list. `scripts/eval_classifier.py` = the real classifier on the set: a hit = overlap with the label and nothing extra; targets overall ≥ 90% and logging ≥ 98%; per-category accuracy, confusion matrix, misses. About 20% of the set is `held_out` (every 5th per main category): scored separately, its misses never printed (only `--show-held-out`), never tuned against; labels are never changed to raise a score. - **Offers to write (reply_rules.WRITE_OFFERS):** "Want me to add/log/save/mark…?", "I can add…", "I'll log…" are allowed only when a tool that can do it is offered this turn (respond passes the turn's offered tools); otherwise rewrite, then trim. - **GSSI knowledge (M4 Part D):**
  - **Index:** `scripts/ingest_gssi.py` reads `docs/gssi_sources.txt` (22 URLs, normalized: lowercase path, `/en/` prefix). For each article it uses a page or PDF saved in `data/gssi_raw/`, or one fetched earlier (`data/gssi_raw/fetched/`). **gssiweb.org is manual only** (`ingest.MANUAL_ONLY_HOSTS`, decided 2026-11-09): it is never requested; new GSSI pages are saved by hand from a browser. The 22 pages fetched on 2026-11-09 (httpx, our User-Agent, 3 s apart, before the decision; curl had been blocked by the site's bot wall) are kept and reused; each was checked (canonical + og:url = its listed URL, title matches, 2,300–8,500 words, no bot-check page).
  - **Other hosts (polite fetch):** robots.txt first (401/403 or a bot-check page = not allowed; an HTML page in its place = no rules), our User-Agent, 3 s apart, redirects followed; a 401/403 or bot-check page from a host stops every further request to it for the run. Bot check = "Request unsuccessful" / "Incapsula incident" (not the word Incapsula alone: real gssiweb.org pages load its monitoring script).
  - **Chunks:** trafilatura (HTML) / pypdf (PDF), cut at the references, 500-token chunks with 60 overlapping (cl100k). Metadata: heading, title, url, year. Stored in Chroma at `data/gssi_index/` (gitignored) with our own embeddings (job `embeddings`).
  - **Re-runs:** an unchanged text is skipped (sha256), so a second run is a no-op; a URL taken off the list leaves the index.
  - **Report:** blocked, failed, listing pages and unmatched files.
- **MCP:** `mcp_servers/gssi/server.py` (FastMCP, stdio) has one tool, `search_gssi(query, k)` → {results: [title, url, section, year, passage ≤ 700 chars]}.
  - `mcp_servers/gssi/index.py` imports nothing from core/, and the server gets only the env variables `config/mcp.yaml` lists (OPENAI_API_KEY).
  - `core/mcp_tools.py` holds one persistent session per server on a background event loop (langchain-mcp-adapters) and calls tools with a 15 s timeout; down, slow or broken → None, and the server is started again on the next call.
  - The agent's `search_gssi` tool is ours (fixed schema). It returns the passages, or `{"available": false, note: answer from general knowledge, approximate, no link}`.
  - Knowledge tools (`agent.KNOWLEDGE_TOOLS`) are offered only to skills that list them (fueling_hydration, goal_program), never to "other". Scripted tests get made-up passages (`conftest.fake_gssi`); live tests use the real server.
- **Citations (`core/citations.py`):** search_gssi numbers its results across the turn ([1], [2]; an article keeps its number). The coach writes a marker only after a claim GSSI makes; its own advice needs none (uncited = the coach's own answer). In respond, `check_markers` checks every marker: each part of the claim before it (split at ; : — and ", so/and/but", minus "GSSI notes that…" and minus parts about their own day) must be said by one sentence of a passage of n that the coach was given: key terms ≥ 0.55 of the part's and embedding similarity ≥ 0.68 (text-embedding-3-small). Unsupported → the marker is removed and the sentence stays; no regenerate; if the check can't run, no marker is kept. Tuned for precision on 108 judge-labeled claims from the live M4-11..13 runs (16 of 17 kept markers judge-supported; about two thirds of judge-supported markers are removed too). Each check is a `runs` row (kind citation_check, with the passages). Then `finish` turns a pasted source url into its marker, drops markers no result has, appends one `Source [n]: GSSI – Title <canonical url>` line per marker left (none when none is left) and one `Amounts: GSSI – A <url> · B <url>` line for the articles behind code-built amounts. Telegram sends every reply in HTML mode with link previews off (`citations.to_html`): all text escaped, and only urls in docs/gssi_sources.txt become links (`Source: <a href="url">GSSI – Title</a>`, `Amounts: GSSI – <a>A</a> · <a>B</a>`).
- **Source rules (reply_rules):** 12+ words in a row shared with a passage is a copy (`copied`): rewrite, then those sentences are trimmed. No marker is required. A rewrite that talks about rewriting ("paste the reply…") is rejected and the draft trimmed instead; "one line from me" is a banned phrase. When a knowledge tool ran, the agent's own line is kept next to code-built text.
- **The own line stays on the plan's topics (2026-11-10):** next to a code-built fueling plan, the agent's line may only talk about topics the plan text has (`reply_rules.topics`: caffeine, sodium, drinking, carbs, protein, by their words; "energy drink" is caffeine). Off-plan ("stick to its caffeine timing" next to a plan without caffeine) → one rewrite, else the own line is dropped (`TurnFacts.plan_topics`, `OFF_PLAN` in `_within_rules`).
- **Tool results carry facts only (2026-11-09):** an instruction in a tool result gets read back as the reply, so no tool result has a field named note / guidance / hint / instructions / how_to_reply, or a sentence starting like an order ("Don't…", "Do not…", "Say…", "Never…", "Answer…", "Ask…", "Call…", "Use…"); refusals say what happened ("could_not_read", "nothing was removed"). What to do with a result lives in the skill bodies and `prompts/agent.md` (sent_as_is → don't repeat it; could_not_read → ask again). Factual fields once called note are `detail` (get_score parts), `status` ("today, still going"), `coverage` (90-day note), `time_read`. `reply_rules.instructions()` finds instruction-like text; every scripted test fails if a tool result it saw has any (`ScriptedChat.orders_seen`). Echo guard (`reply_rules.without_echo`, every reply and rewrite): a sentence sharing 8 words in a row with instruction-like text left in this turn's tool results is dropped; facts the coach restates (food logged, plan lines, the ring-only sentence) are never compared. The GSSI 12-word rule (retrieved passages) is separate.
- **After a log, confirm and stop (Part A/C follow-up, 2026-11-09):** when log_food / add_manual_workout / mark_done ran, their message asked nothing and nothing is missing (no write refused, no workout Oura lacks), a question or an offer in the reply ("want me to correct it?", "let me know") is a violation (`reply_rules.TurnFacts.after_log`, `LOG_OFFERS`): rewrite, then trim. A tacked-on offer made the next food message read as an answer (scenarios 17-18).
- **Edits need correction intent:** edit_food / remove_food refuse (nothing changed) unless their message says so ("actually", "correction", "change", "it was", "wrong", "remove", "delete", "undo"…) or answers the coach's question about which entry; otherwise named food is a new entry ("had a banana" after a log = a new row).
- **Plan flags the reply can't contradict:** fueling_plan returns `carb_load` (False = no extra carbs the day before); with False, "boost / load / extra / more carbs" in the reply is a violation (`TurnFacts.carb_load`, `MORE_CARBS`).
- **Amounts are cited by code:** fueling_plan returns the article behind each range it used (`code_sources`, titles in `config/fueling.yaml`), and `citations.finish` lists them on one `Amounts:` line; the coach's [n] markers are only for what GSSI says in words. G rubric (fueling_hydration, goal_program): "Every [n]-cited claim is supported by passage n" (`tests/conftest.judge_citations`, used by the live Part D tests).
- **Amounts in fueling answers come only from tools:** next to a code-built fueling plan the agent's line is at most two sentences with no amount, no recap of the plan ("During: …") and no question (`reply_rules.own_line`); in a fueling_hydration turn any sentence stating an amount no tool returned this turn is dropped (`reply_rules.amounts_from`). When the coach asked for their weight in this conversation and their message gives one ("I'm 62 kg"), the agent's first call is forced to `save_body_weight` (tool_choice), which redoes the earlier fueling plan in grams (code-built, sent as is).
- **Fueling (`modules/nutrition/fueling.py`, pure; tool `fueling_plan`):** amounts around a run from `config/fueling.yaml`, each range citing its GSSI article (checked against the indexed text 2026-11-09; comments paraphrase, never quote). Every number is GSSI's; two conditions are ours and labeled `ours:` in the file (the 60–90 g/h tier only past 21.1 km; sodium from 90 min). Body weight: goals.yaml override, else Oura `personal_info.weight` (fixtures: 69.9 kg), else the saved fact; never a default.
  - **Run length:** minutes they wrote (a number not in their messages is ignored), else distance × their median Oura pace (3–12 min/km only), else their longest run in 4 weeks, else 75.
  - **Parts:** day before (none under 90 min; 7–12 g/kg from 90; race 10–12 g/kg for 36–48 h), before (none under 60 min; 1–4 g/kg, 1–4 h, from 60), during (none under 60 min; 30–60 g/h from 60 min; 60–90 g/h only past 2.5 h AND longer than 21.1 km, so a half marathon is always 30–60 g/h), fluids (thirst under 90 min; planned after, loss < 2% of weight; sodium 20–40 mmol/L = 460–920 mg/L), caffeine (1.5–3 mg/kg from the caffeine article; about 60 min before, the ISSN advice reported in the sleep article), after (20–25 g protein; for a hard session again that day, 1.0–1.2 g/kg carbs an hour for 4 h).
  - **Inputs:** recent carbs = average over logged days of the last 7.
  - **Sent as built:** the agent's own line next to it states no amount (`reply_rules.without_amounts`), and a repeated identical call is sent once.
- **Body weight:** goals.yaml `nutrition.weight_kg` > Oura personal_info > a saved fact `Body weight: 62 kg` (memory kind `body`, written and read by code via the nutrition tool `save_body_weight(weight, unit)`, lb converted in code). ## Oura data notes (observed in fixtures, 2026-10-07)
- Daily endpoints return one record per `day`. Querying start=D-7, end=D+1 returned D-7..D.
- `workout` can return records dated before `start_date`, so always filter by `day`.
- `sleep` has several periods per day (`type`: `long_sleep`, `sleep`). Main night = `long_sleep`. HRV = `average_hrv`, resting HR = `lowest_heart_rate`.
- Durations (`total_sleep_duration`, `stress_high`, `recovery_high`) are in seconds.
- `heartrate` samples: `timestamp` in UTC, `bpm`, `source` in {awake, rest, workout, live}. Workout samples are much denser, so `hr_avg` leaves them out.
- `daily_readiness.contributors.resting_heart_rate` is a 0–100 score, not bpm.

# M3.2 — Core + modules refactor: plan

> Approved 2026-10-16 with 4 changes (applied below): training score with no plan, egg diet seed, first-person claim check, `git tag m3.1` first.

## Context

M1–M3.1 work, but everything is built around one person and a fixed intent router: a `router.md` LLM call picks one of 7 actions, there are 9 slash commands, and "Sorry, I'm not sure what you mean" is the fallback. Personal details ("vegetarian, Indian") are written into the prompts, and one LangGraph thread per check-in is the only conversation memory. M3.2 turns this into a **shared core + plug-in modules + device connectors**: a tool-calling agent, multi-user tables, short- and long-term memory, an Oura-defined day, and a deterministic daily score. It stays reactive only (nothing fires on its own), and `python bot.py --fixtures` keeps working after every phase.

Decisions you made (2026-10-15):
- **Day boundary = main-sleep START.** An event after midnight that comes before the night's `long_sleep.bedtime_start` belongs to the previous day.
- **Context notes become saved memory with optional dates.** They are written only when you ask; the `context_notes` rows migrate in.
- **Package layout:** `core/ modules/ connectors/ channels/`.
- **Override = consult once.** On a conflict, the bot names what it would do instead and the specific rule it would skip, in 1–2 plain lines (e.g. "Readiness 64 and you did HIIT yesterday, so I'd suggest a 30-min easy run instead. Still want HIIT?"). Yes → it plans what you asked; only free time and the 21:00 cutoff still apply, and each skipped rule is recorded as `user_choice`. No, or picking its suggestion → it plans that. It pushes back only once per request.

## 3. Data model changes

| Table | Change |

The rename clears the clash with chat sessions. `source='unplanned'` rows move to `manual_workouts`. |

| `memory` **new** | `id, user_id, text, kind (goal/diet/preference/instruction/context), start_date NULL, end_date NULL, created_at`. `context_notes` rows are copied in as `kind='context'` with dates. Seeded: "Vegetarian, eats eggs", "Prefers Indian food" (goals.yaml itself is not modified). |
| `messages` **new** | `id, user_id, chat_session_id, ts, role (user/assistant), text`. |
| `chat_sessions` **new** | `id, user_id, started_at, last_user_at, thread_id`. |
| `oura_cache` **new** | `user_id, fetched_at, start_date, end_date, raw_json`. 10-min TTL. |
| `daily_scores` **new** | `user_id, day, score, components_json, final (0/1), computed_at`, PK (user_id, day). |
| `meal_suggestions` **new** | `id, user_id, day, dish, created_at` (so suggestions don't repeat). |
| `daily_log`, `runs` | `+ user_id` (daily_log PK becomes (user_id, date): table rebuilt). |
| `context_notes` | Left in place, read-only, dropped in M4 after a check. |

**Migration (`core/db.py`, one function per step, each guarded by "does this column/table exist"):**
1. `_needs_migration()` detects M3.1 (no `users` table). → `backup_db()` → prints `oura_coach.backup-YYYYMMDD-HHMMSS.db`. Aborts if the backup raises. Same for demo.db.
2. One transaction: create the new tables → insert user 1 + settings → `ALTER TABLE ADD COLUMN user_id INTEGER NOT NULL DEFAULT 1` on food_log/runs → rename `sessions`→`plans` and add columns → copy unplanned rows into `manual_workouts` and delete them from plans → rebuild `daily_log` with the composite PK → copy context_notes into memory → seed diet facts.
3. Verify the row counts (food 17, plans + manual = 9, memory ≥ 1) before commit; roll back on a mismatch.
4. Test: `tests/test_db_migration.py` builds an M3.1-shaped DB, migrates it, checks every row and that the backup exists. Tokens are compared byte for byte before and after.

## 4. Phases

### Phase 1 — Foundation (no behaviour change for the person)
- **0.** `git tag m3.1` on the current commit (34c6eb6) before any change.
- **1.1** Package move + `users`/`user_settings` + `user_id` everywhere. Every `db.*` function takes `user_id` first. `Coach` resolves the user from the chat id.
- **1.2** `chat_sessions.py`: `touch(user, ts) → session` (new if gap > `session_gap_min`), `log_message`, thread id `session-{user_id}-{YYYYMMDDHHMM}`.
- **1.3** `memory.py` + seeding; the "vegetarian, Indian" lines leave `food.md`/`plan.md`. Memory is passed as context instead.
- **1.4** `day.py`: `day_bounds(user, D) = [max(midnight D, long_sleep(D).bedtime_start) … same for D+1)`, using cached Oura sleep (no fetch; falls back to midnight). `day_of(user, ts)` = the D whose bounds contain ts. Food totals, plans, score and "today" all go through it. Food rows keep `timestamp` only, and the day is computed when read, so a 1am snack that got the fallback day lands right once Oura syncs.
- **1.5** `modules/base.py` Protocol (exact signatures from the brief) + `registry.py`.
- **1.6** `connectors/base.py` `HealthSource(readiness, sleep, workouts, activity)`; `OuraSource` wraps `OuraClient.fetch_range` with `oura_cache` (TTL 10 min, `refresh=True` forces it); `ManualSource.workouts`; `health.py` merges them with the existing `activity.merge_activity`. There is no write path to Oura data. The old `today.py` splits into `connectors/health.py` (device data) and `modules/*/context()` (module views).
- **Pause:** `pytest -q` (existing tests ported to the new imports), migration on a copy of oura_coach.db, `python bot.py --fixtures` still runs the old router flow.

### Phase 2 — The agent
- **Graph `core/agent.py`** (per chat-session thread, SqliteSaver, state = `messages` with `add_messages` + `user_id`, `now`, `tool_log`):
  `ingest → agent ⇄ tools (ToolNode) → respond → END`
  - `ingest`: touch the session and log the inbound message. Build a system context: saved memory, each enabled module's `context(user, day)` (short, no fetch unless needed), pending state (open check-in / pending consult, plus whether that check-in came from an earlier session → the "Still want to check in today?" line), time and day. History = this thread's messages trimmed to the last ~10 user/assistant turns (tool messages kept with their AI turn).
  - `agent`: `ChatOpenAI(OPENAI_MODEL).bind_tools(enabled tools)`; logged to `runs`.
  - `respond`: if a plan tool ran this turn, its code-formatted text is sent **verbatim** (the plan format is not the LLM's). Otherwise `reply_rules.check(draft, tool_log)` runs: ≤3 lines, ≤60 words, no banned terms (band, push/maintain/recover, intensity N, remaining_today, window, null, snake_case), and no claimed action without the matching tool. The check matches **first-person claims only** ("I logged", "I've updated", "I synced", "I'll resend"), never the bare word: "logged it"/"saved" after "I/I've/I have" → log_food|remember, "I removed/deleted" → remove_food|forget, "I updated/changed/edited" → edit_food, "I synced/refreshed/pulled" → refresh_health, "I'll resend/I'll send" always fails. On a failure it regenerates once with the reason; if it still fails, it trims to fit and replaces the false claim with what the tools actually returned.
- Every interrupt is removed. A check-in is now DB state (`plans.status = awaiting_checkin`), not a paused graph, so a check-in never blocks a session.
- **Tools:** the exact list from the brief. `get_today` = plan/food/activity summary (fetches Oura only if the question is about activity/sleep/readiness: `get_today(include_health: bool)`). The `list_food` output carries entry ids and positions, so "the pizza" or "the second one" resolves against it plus history.
- **Commands:** only `/start` and `/help` (built from the enabled modules' `help_lines()`). Greeting, voice and "expired check-in" are handled in `channels/telegram.py` (voice: fixed reply) and in agent prompt rules (greeting = readiness + what I can do).
- **Pause:** replay scenarios 1, 8, 9, 11, 12 pass; Telegram smoke test with fixtures.

### Phase 3 — Training module
> Done 2026-10-18, approved with changes (per-block done, consult expiry by time with no plan, late = after the cutoff or before the morning, "no" = the stored suggestion). What was built is in CLAUDE.md Decisions; the eval set is `docs/scenarios.md`.

- `checkin.py`: one structured LLM call → `{energy 1–5, soreness 0–5, request: {blocks:[{type, duration_min}]} | null, feeling, constraints}`. Soreness 0 is valid (the schema and `effective_band` thresholds are unchanged). The regex parser stays as a fast path for bare "4 2".
- `planner.py` (the old graph minus the interrupt, compiled without a checkpointer, still drawn and still in Studio): `fetch → baseline → gather → [request?] → plan | rest_plan | late_rest → policy → consult? → log`.
  - **Consult:** run `policy_check` on the *requested* plan. If any override has `changes_type` (or the requested intensity gets capped from hard), save the request as `awaiting_confirm` and return a 1–2 line nudge built in code from the deciding overrides' `plain` text plus the band suggestion ("…so I'd suggest a 30-min easy run instead. Still want HIIT?"). `confirm_override(yes)`: yes → `policy_check(..., user_choice=True)` skips every rule except `_fit_window`/cutoff and records each skipped one as `{rule: user_choice, skipped: <rule>}`. no → plan the suggestion. The pending row clears either way, so there is never a second consult.
  - **Blocks:** `Plan.blocks: list[Block]`. Each block goes through the type rules, the day is hard if any block is hard, and the window fits the total duration. A single-block plan formats exactly as today.
  - A new check-in abandons today's open plans that aren't done. A check-in after `score_cutoff` → rest + sleep note, with no LLM plan call (reuses `rest_plan`).
- `mark_done`: `refresh_health()` → `match_open_plans` (existing) → if Oura matched, set `actual_start/end` from Oura (`done_by=oura`, final). Otherwise reply "Oura hasn't shown it yet. Want me to add it with a time?" → `add_manual_workout`.
- `score()`: done as planned = 1.0; done but lighter (a lower type or shorter than 70% of the planned minutes) = 0.5; planned rest respected (no hard workout) = 1.0; missed = 0; nothing planned → full credit for any Oura or manual workout (a walk counts only at 20+ min), and 0 when there was no activity at all (never neutral).
- **Pause:** scenarios 6, 7, 10 + `run.py --fixtures` variants.

### Phase 4 — Nutrition module
> Done 2026-10-18, with additions: list_food takes any past day; suggest_meal enforces variety in code (no dish from the last 5 days of ideas or 2 days of eating) and gives grams + household portions; `meal_recipe` for "the second one" / "make it higher protein"; edit_food `feedback`; a guard against removing ambiguous entries. Built as described in CLAUDE.md Decisions.

- `log_food(text, time, user_numbers)`: user-stated numbers override the matching estimate fields and are recorded in `user_numbers_json`. Confirmation is one line.
- `edit_food(entry_id, fields)`: updates that row in place and re-estimates fields the user didn't state when the description changes (e.g. "cheese pizza with olives"). Stated numbers win. It never inserts a row.
- `remove_food(entry_ids)`: deletes and returns what was removed. `list_food(day)` uses `day_bounds`.
- `suggest_meal(constraints, ingredients)`: LLM with remaining-for-day (code), diet facts from memory, the last 5 days of `meal_suggestions` (to avoid), and frequent foods from food_log. Sized for one meal. 1–2 options are saved to `meal_suggestions`. Fallback meals move from `nutrition.py` to `config/meals.yaml`, keyed by diet.
- `score()`: protein vs target (linear to 100% at target); calories inside ±10% of target = full (moderate), sloping to 0 at ±30%; **below the calorie floor (`score.yaml`, default 0.6 × target, only checked after the cutoff) = 0**; meals logged ≥ 3 = full. No food → 0, breakdown "not logged" (`score.yaml: no_food_scores_zero: true`).
- **Pause:** scenarios 2, 3, 4, 5.

### Phase 5 — Daily score
- `config/score.yaml`: `templates.endurance_body_comp.{light,moderate,intense}` → weights (training 35, nutrition 30, recovery 20, movement 15 at moderate), thresholds and step targets (light 6k / moderate 8k / intense 10k).
- Recovery and Movement are **core components in `score.py`** (device data from `connectors/health.py`, not modules you turn on): recovery = readiness and sleep score scaled 60→0 … 85→1; movement = steps / target.
- `compute_score(inputs) → {score, components:[{name, points, max, note}]}` is a pure function. `get_score(day)` collects the inputs and returns them. The LLM only words the breakdown from `components[].note`. Final score: reactive only, so on the first message after the cutoff (or any later day) the score is computed for every unfinalized past day and stored with `final=1`. No streaks.
- **Pause:** scenario 14 + unit tests for every component.

## 5. Session thread_id trade-off (for the doc)
- **Pros:** the agent remembers the conversation inside a session, which "that", "the second one" and "make it higher protein" need. Tool calls and results stay in the thread, so references resolve to real entry ids. One thread per burst of conversation keeps the context small and cheap.
- **Cons:** nothing carries over after 15 min except saved memory and DB state (by design). A check-in can no longer be a paused graph that lasts for hours, so it moves to DB state. The checkpoint DB grows by one thread per session, which is fine at this scale; M4 can prune threads older than N days. A crash mid-turn leaves a half-finished thread that the next session never resumes. That's acceptable because every write is a tool that commits on its own.

## 6. Risks
- **Large move + migration at once.** Mitigation: Phase 1 is a refactor with no behaviour change, has its own pause and tests, and runs the migration on a copy of the live DB first (`cp oura_coach.db /tmp-scratch/…` → `init_db`).
- **LLM picks the wrong tool, or claims actions it didn't take.** `respond` checks it in code; the live replay suite measures it. gpt-5-mini tool-calling quality is the main unknown. If it's weak, `OPENAI_MODEL` can be raised without code changes.
- **Day boundary at 1am live:** Oura has no sleep record yet → calendar day. It self-corrects on read once Oura syncs (the day is not stored for food); stored plans use the day at plan time.
- **Reply-length rule vs useful answers (recipes):** recipe requests are exempt from the 3-line cap (still plain words). I'll flag it if you want it stricter.
- **Removing commands** removes the deterministic /why and /undo. `explain_plan` and `remove_food` replace them through the agent.
- **gpt-5 rejects temperature:** still not set, so regenerations aren't guaranteed to differ. The correction message carries the reason.
